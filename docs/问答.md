# 问答

## Q1 扫描为什么要「单向逼近」？

**对你意味着**：扫出来的图像是**对齐的** —— 相邻点之间的距离准确，拼图或逐点对比不会错位。你不需要做任何设置。

**一句话**：扫描时，台子**每个点都从同一个方向走过去**，不是来回走。

**为什么不能来回走**

| 走法 | 台子实际停在哪 | 结果 |
|---|---|---|
| 每点从同一侧走（本项目默认） | 所有点偏同一个方向，互相抵消 | 点间距准确，**图像对齐** |
| 来回走（有的点从左、有的从右） | 有的偏左、有的偏右，相差约 0.1 µm | 点间距忽大忽小，**图像错位** |

**你会遇到的几种情况**

| 情况 | 你会看到 | 你要做什么 |
|---|---|---|
| 扫描进行中 | 台子从起点向终点**一路单向前进**，一步一停、每点采图 | 不用管，让它跑 |
| 想反着扫（从大到小） | 起点填大数、终点填小数 | 直接填，后端会自己反过来逼近 |
| 扫描中或暂停时想手动挪台子 | 被拒绝，提示「扫描进行中或已暂停，请先中止再手动操作」 | 先点「中止」，再手动操作 |
| 起点离行程端点不到 2 µm（比如从 0 开始扫） | 首点会比其余点偏约 0.1 µm，日志里有一条警告 | 起点往里让 2 µm（0→100 改成 2→100） |
| 扫描跑完看结果 | 点位表里有每点的「实际」「间距」和「偏差 (nm)」 | 看偏差与间距列；偏得离谱的点会被判无效并中止扫描，不会悄悄入库 |

**这是台子的性质，不是软件的选择**：同一个位置从两个方向走过去，停的地方差约 0.1 µm。软件能做的只有保证「每个点都从同一侧走」。另一台台子（芯明天）也照这个走法 —— 那边理由没那么强，但这条不花钱。

*依据：`docs/pi/设备认识账.xml` A3、`backend/scanner.py` `_approach_start`、`backend/config.py` APPROACH_OFFSET_UM*

## Q2 台子读出的位置是相对什么位置？为什么会有抖动？跟真实位置什么关系？

**对你意味着**：读数是**相对台子自己零点**的位移 —— 它能回答「稳没稳、走了多远」，答不了「绝对在哪儿」。

| 问题 | 回答 |
|---|---|
| 相对什么位置？ | 台子自己那只位置传感器的零点（零点定在控制器里），不是机械挡块、不是样品、不是大地 |
| 本仓库会动零点吗？ | 不会。换了控制器或重新调过零，同一个物理位置报出来的数就不一样 |
| 为什么一直跳？ | 传感器噪声 σ 30~50 nm + 数字最小刻度 3.2 nm + 机械/环境振动（同一个传感器分不出是噪声还是真在动）+ 走完后约 25 nm 的蠕变 |
| 跳多少算正常？ | 静止时末位跳动正常；10 秒峰峰 0.3 µm 也是噪声的正常极值（≈6σ），不是台子真动了这么多 |
| 跟真实位置什么关系？ | 相对量（点间距、稳没稳）可信；绝对位置要靠外部标定（干涉仪、显微镜刻度），本仓库不做 |

上面数字是**芯明天那台**的实测量级；PI 那台只确认过「伺服不动、不漂移」。

**一句话**：它自己跟自己永远一致，所以「稳没稳」它说了算；它看不到自己的零点和刻度准不准，所以「绝对在哪儿」它说了不算。

*依据：`docs/xmt/设备认识账.xml` A4 / A5 / A6 / E11、`docs/pi/设备认识账.xml` B1、`backend/config.py` XMT_ARRIVAL_TOL_UM*

## Q3 后端是怎么判断「可以采图了」的？

**对你意味着**：你不需要判断台子稳没稳。后端**先等一段时间、再看一眼位置**：位置落在目标附近就采图，采图那一刻的位置照实记进点位表。等多久由你在扫描页的「稳定延时」里设。

| | PI E-709 | 芯明天 E53.D1S-H |
|---|---|---|
| 靠什么判断 | 控制器给的**硬件到位信号**（它自己知道到了） | **后端读一次位置**：落在目标 ±0.2 µm 内才算到位（这台设备没有到位信号） |
| 界面上的「稳定延时」是什么 | 到位信号**之后**再等的额外时间 | **唯一的等待**：先等满它，再读那一次位置 |
| 默认值（界面上可改） | 100 ms | 300 ms |
| 等不到会怎样 | 10 秒还没等到信号 → 该点无效、整条扫描失败 | 读一次发现超差 → 该点无效、**不采图、不入库**、整条扫描失败 |

流程：**移动 → 等到位（PI：信号 + 延时；XMT：等满延时 + 读一次回）→ 按步距校验偏差 → 采图并记下当时的位置 → 下一个点**

**芯明天这台为什么改成「等固定时间」**

| 原来的做法 | 现在为什么不要它 |
|---|---|
| 连着几次读数不变才算停稳 | 台子慢慢蠕变时这招本来就会误判成「停稳」；而设备后面板两个整定旋钮一动，判据参数就得重测 —— 维护成本高、信息又少 |
| 每 50 ms 采样 + 随机抖动 | 一并删掉；现在只读一次位置 |

**你会遇到的几种情况**

| 情况 | 你会看到 | 你要做什么 |
|---|---|---|
| 等待设得太短（比如 50 ms） | 多数情况是**直接判该点未到位、整条扫描停下**（那时读数还没进 ±0.2 µm）。只有读数已经进了容差、台子还在慢慢蠕变时，才会不声不响地采到还在动的点 | 把「稳定延时」调大（几百 ms 起）；点位表的「间距」列能看出实际走到了哪 |
| 台子蠕变、读数慢慢漂 | 记下的是**采图那一刻**的位置，漂多少记多少 | 不用管；想更稳就把延时调大 |
| 设点丢了一帧（台子没动） | 那一点判无效：不采图、不入库、**整条扫描停下**，日志说明原因 | 重扫；步距别小于 0.5 µm（见 Q4 / Q5） |
| 改了后面板那两个整定旋钮 | 原来的等待时间就不准了 | 重新试一个够用的延时 |
| 想看每点**实际**间隔 | 点位表「间距」列 = 相邻两点「实际」之差 | 直接看；和「目标」列对比就知道偏了多少 |

**一句话**：以前是「等台子不动」，现在是「等够时间就采，位置如实记」—— 简单、可预期，代价是**等多久得你自己定对**（定得太短会整条扫描失败，不会悄悄给你错数据）。

*依据：`backend/xmt_stage.py` wait_on_target、`backend/pi_stage.py` wait_on_target、`backend/scanner.py` `_settle_ms` / `_run`、`backend/config.py` 停稳与等待一节、`docs/xmt/设备认识账.xml` E7 / E12*

## Q4 「每点采图前按步距再校验一次偏差」是什么意思？

**对你意味着**：采图前后端还会再查一道 —— 「实际位置 − 目标位置」超过**半个步距**就判这一点无效：**不采图、不入库、整条扫描停下**。

**为什么设备说「到位」还不够**

| 判断 | 谁在判 | 容差 | 盲区 |
|---|---|---|---|
| 第一道 | 设备 / 设备层 | **绝对**（XMT 是 0.2 µm；PI 是控制器自己的到位窗口） | 步距比容差还小时，分不出「真到位」和「压根没动」 |
| 第二道 | 后端扫描器 | **相对**：半个步距 | —— |

它专防**设点丢帧**：台子丢了新设点、停在上一个点没动，这时差值正好是**一个步距**。

| 步距 | 丢帧时差多少 | 设备层怎么看 | 结果 |
|---|---|---|---|
| 0.5 µm | 0.5 µm > 0.2 | 判「没到位」 | 设备层自己就发现了 |
| **0.15 µm** | 0.15 µm **< 0.2** | 判「**到位**」 | **静默错点** —— 拿上一个位置的图当成这一点的图 |

**为什么取半步距**：丢帧永远差「整整一个步距」，所以这条**不管步距多小、设备容差多大都成立**；而它只收半个步距，不会误伤正常的定位误差。

**触发之后**：该点不采图、不入库；整条扫描就地 failed（不跳过、不继续）；跑过的点都在库里，半截那条由人在界面上手动删。

**步距该设多大**（XMT 实测偏差：偏置 90 nm + 抖动 30~50 nm，最坏 120 nm）

| 步距 | 阈值（半步距） | 余量 | 结论 |
|---|---|---|---|
| 1 µm | 500 nm | 4 倍 | 稳 |
| 0.5 µm | 250 nm | 约 2 倍 | 可用（长期假失败率未评估） |
| 0.2 µm | 100 nm | 比最坏偏差还小 | 会被随机打掉点，别用 |

*依据：`backend/scanner.py` `_run`、`backend/config.py` SCAN_ARRIVAL_FRACTION、`docs/xmt/设备认识账.xml` P0 / B10 / E8 / E12、`AGENTS.md`*

## Q5 手动保存的帧是原生数据吗？跟存成 PNG 还是 TIFF 有关系吗？

**对你意味着**：文件里存的就是相机交出来的原值；**格式不影响数据真实度** —— 保真靠的是「无损编码 + 位深够 + 没动过数据」这三条。

| 环节 | 保存的文件 |
|---|---|
| 幅面 | 原生全幅 1440×1080（不裁剪，也不用预览 ROI） |
| 位深 | 16 位灰度，像素写的就是原值（0~1022 ADU） |
| 处理 | 无 —— 不平滑、不扣背景、不归一化、不伪彩、不重采样 |
| 朝向 | 永远是传感器朝向（预览转 90° 只影响看的那一份） |
| 元数据 | 曝光与质心写在文件自己的 tEXt 块里，图像自证 |
| 压缩 | zlib 无损（PNG 规范里没有有损模式） |

| 换成 TIFF 会怎样 | 说明 |
|---|---|
| 像素数据 | **一模一样** —— 前提是无损编码、位深 ≥16、不重采样 |
| 注意 | TIFF 是容器，**里面也能塞 JPEG**：「存成 TIFF」本身不保证无损 |
| 元数据 | 要改写成 TIFF tag，读写代码得重写 |
| 工具链 | ImageJ / Fiji 更顺 |

**文件 vs 显示**（唯一容易误会的地方）

| | 文件 | 界面 / 浏览器 |
|---|---|---|
| 位深 | 16 位原值 | 右移 2 位 → 8 位 |
| 朝向 | 传感器朝向 | 可按预览朝向转 |
| 用途 | **定量**（ImageJ / Python 读） | 看构图、找光斑 |

「看着对」不等于「存的是那个」：值只占 0~1022，按满量程渲染打开就是黑的 —— 这点 PNG、TIFF 一样。

**「原生」的边界**：指「SDK 给什么就存什么」，不等于传感器裸数据 —— SDK 报 12 位 ADC 而实测上限 1022（约 10 位），中间那两位的来历未证实。

*依据：`backend/thorlabs_ccd.py:775-806`、`AGENTS.md`「索雷博 CS165MU」、`docs/thorlabs/设备认识账.xml` A3 / B1 / E7*
