# 文档编写规范

**怎么用**：写文档前读这一页。

总纲：**上层只定“要什么”，下层只答“给到什么效果”，用逐字照抄的名字互相指认，机器对账兜底。**
冲突时：需求 > 设计 > 其余；文档与代码冲突，先改需求或先问，不在实现里悄悄改。

## 一、体系：四层，一份文档只回答一个问题

| 层 | 只回答 | 不回答 | 什么时候写 |
| --- | --- | --- | --- |
| 规程（AGENTS.md） | 怎么干活：选型、约束、构建发布、红线 | 需求（不判“该不该做”）、机制 | 一次，随项目改 |
| 需求 | 要什么、砍掉什么 | 方案、选型、分层、代码组织 | 先于一切设计 |
| 设计（每部分一份） | 这一层对外承诺什么效果、出什么事说什么 | 机制（住代码）、需求（指回上游）、别层的效果 | 需求定下来之后 |
| 附件（需要时才出现） | 词表：一个词只解释一次；地图：有问题读哪份；底本：外部事实快照 | 需求、机制 | 出现第二个同类例子时 |

- 三律：**一个部分一份文档**；**总是一起改的放同一组**；**一个词只定义一次**。
- 文件：一个部分一个文件，文件名就是读者找它的地址；要顺序就编号（编号只表阅读顺序）；词表、地图各一份，底本与示意图放子目录。
- 一行装不下就分文件、不另开层（规程可拆“通用/项目”两份）；决策记录这类新类型，等出现第二份同类文档再单开一行。

## 二、从零写一份：五步

1. **定问题**——这份回答哪个问题、属于哪一层？一层一个问题。
2. **找家**——已有文档里有没有它的家？有就改那份；合并拆分等第二个例子出现。
3. **写认领表**——设计类文档开头一行一条需求，名字逐字照抄。
4. **写承诺**——一节一件事，只写“承诺什么、出什么事会说什么”。
5. **划边界、挂地图**——结尾把不管的事逐条点名去处；地图加一行；跑一次对账。

## 三、两种正文怎么写

**需求（要什么）**

- 只写需求不写方案；**可验收的数属于需求**（默认值、上限、阈值），写进条目。
- 一条一件事、能判做到没做到；禁“尽量/优雅/高性能”这类没法判断的词。讲大意，字段与回收时机不写。
- 优先级只标在目标上（必须/应该/可选）；**非目标是同级别的结论**，写清“不做什么”。
- 目标与非目标各分两栏：落在屏幕上的归界面栏，其余归后端栏。
- 自包含（不留只在讨论里用过的代号）；**拿不准的进「待定」**，不猜一个当结论。

**设计（给到什么效果）**

- 开头一段：这份讲什么、边界一句（“机制住代码/数据里”）、词表与需求指路、邻居指路。
- 认领表：一行一条需求，名字逐字照抄，回答列写“这一层给出的回答”；正文每处机制指回它认领的那一行。
- 只讲效果：不写为什么这样设计、不写备选与代价。
- 不写代码里的名字与目录名；**例外**是契约本身（配置键、表列、文件名、可验收的数）。
- 结尾「这里不管的事」：逐条点名去处；长文开头给一句“怎么读”。
- 要改承诺：先改需求或先问。

**骨架（照抄）**

```
# <部分>设计
**一句话：这份讲什么、不讲什么。** 词在 <词表>；需求在上游（<需求文档>）；<邻居> 见 <哪份>。
## 这份设计认领了哪几条需求
| 需求 | 这一层给出的回答 |
| --- | --- |
| 「任务可以取消」 | 取消一到就落账，跑着的那一步自己收尾；已收到的结果照实留下 |
## 一、<一件事>
承诺：……。出什么事会说什么：……。
## 这里不管的事
- <某事> 归 <哪份文档 / 代码>。
```

需求条目长这样：`- **<条目名>（必须）。** 一句话，可判做到没做到。`
认领格只有两种写法：一串「逐字条目名」，或「没有对应需求（待定）」。

## 四、引用与命名（机器可核）

- 指回需求：**「见」+「」包住的逐字名字**，中间不夹别的字；名字取自需求文档的条目名/章节名，或本文档自己定过的标题、加粗名字。
- **每处机制都要指**，不能只写在开头；指不够细就补节名（`…见 <文档> §三`）；代码注释里指需求，名字用「」逐字包住。
- **一个词只有一处定义**（词表）：加粗的名字是唯一写法，旧叫法另收一节——别处再解释一遍就是漏改。
- 名字全线一致：代码里的名字 = 文档里的名字 = 账上的名字 = 界面上说的名字。

## 五、行文

- 每节第一句给结论；一节一件事，标题写清这件事，不写“其它”。
- 禁词：尽量、优雅、高性能、合理、完善、大概、视情况、“以后再说”。
- 表格只作对照（端口表、认领表），不拿它当正文；说条目名一律「」逐字照抄。
- 一份文档只讲一个部分；一屏读不完先拆节，真要拆两份，等有两个读者群再说。

## 六、几样小东西

- **状态**：文首标成形/待定；设计不写版本史（历史住版本控制）；日期只给外部事实标。
- **词表**：每条一句话，直击这个词是什么；只管“这个词在本仓什么意思”。
- **底本**：文首写来源 + 抓取日期，只记一处，写明“上游会变、动手前重抓”。
- **图**：只解释已经写过的承诺，不新增；单文件离线最好；挂回它解释的那一节。
- **注释**：只写最新状态，不写旧的是什么；为什么只在非显然处写一句。

## 七、交付前自检

1. 每条承诺在认领表里有行，每个认领行在正文里有落点；
2. 每个目标都至少被一份设计认领（没认领的进了「没有对应需求（待定）」）；
3. 没有代码里的名字（契约键、文件名、可验收的数是例外），没有“为什么”与备选；
4. 边界每项都有去处；拿不准的都在待定里；
5. 引用全是逐字名字——有条件就把这几条钉成测试（引用逐字、认领格两种写法、改名后全仓旧名清查）；
6. 地图已挂上。

## 八、维护

- **改名是破坏性变更**：跑一次清查，列出全仓引用点，照单改完才算对上。
- 两份总是一起改就合并，谁也不牵动就各自独立，没有读者的删掉。
- 地图过期先修地图，别处过期以该文档自己的第一段为准。
- 套用到现有项目：先写需求 → 给每份设计补认领表与边界 → 再上对账 → 最后收紧行文。

---

总纲：**每个设计决定只有一个家**——归属唯一、接口不变宽；一份知识只解释一次，改根不改补丁。
